# Feature Roadmap and Shared Contracts

This document is the spec every numbered plan in this folder argues from. It fixes the
names, tables, columns and interfaces that more than one plan touches, so plans written
and executed independently still fit together. A plan may add to these contracts; it
must not rename them.

Out of scope for now (deliberately deferred): extra alert channels (Telegram, ntfy,
Discord, Slack, Web Push). Everything below keeps `channel` as a column so they can be
added later without a migration.

## Plans and their order

| # | Plan | Depends on |
| --- | --- | --- |
| 01 | Alert log, daily thresholds, cycle thresholds and pace alert | - |
| 02 | Scheduler tick, stale-router alert, scheduled digest | 01 |
| 03 | Router loop: throttle on breach, script generator, first-run wizard | - |
| 04 | Dashboard insights: live throughput, day drill-down, anomaly flags, outage report | - |
| 05 | Per-device usage | - |
| 06 | Data operations: retention thinning, import, Prometheus metrics | 02 (thinning runs from the tick) |
| 07 | Access: active browser sessions, read-only share link with JSON feed, PWA manifest | - |

Plans 01 to 07 each produce working software on their own. Execute 01 before 02, and 02
before the thinning task of 06. Everything else can run in any order.

## Facts about the deployment (verified 2026-09-12)

- Production runs on Vercel at `https://netmonitor.bilalnasr.com`; the database is
  Supabase (eu-west-1, about 85 ms per query round trip from the dev machine, so every
  page should batch its queries with `Promise.all`).
- The router is a MikroTik hEX lite, RouterOS 7.24.2, single 850 MHz core, 64 MB RAM.
  The WAN interface is `pppoe-out1`. The LAN is `192.168.88.0/24` on `bridge`. The
  `quota-push` scheduler runs every 30 seconds.
- `/tool fetch url=... output=user as-value` on this RouterOS returns the HTTP response
  body under the `data` key. A script can therefore read what `/api/ingest` answers.
- The default-configuration fasttrack rule (`/ip firewall filter`, comment
  `defconf: fasttrack`) is enabled. Fasttracked connections bypass simple queues, so a
  throttle queue only takes effect while that rule is disabled.
- The DHCP server lists two leases: an Archer AX55 Pro (`192.168.88.253`) and the monitor
  PC (`192.168.88.254`). If the Archer runs as a NAT router, every Wi-Fi client is one
  MAC to the MikroTik and per-device accounting cannot separate them. Plan 05 states this
  as a precondition.
- Timezone in settings is `Asia/Beirut`.

## Project conventions every plan follows

- Next.js 16 App Router, TypeScript, `pnpm`. Read `node_modules/next/dist/docs/` before
  writing route or page code; the `connection()` call at the top of a dynamic page and
  `next/root-params` for the locale are the local idioms.
- Every string a person reads comes from `lib/i18n/dictionaries/en.ts` and has an Arabic
  entry in `ar.ts`. The test `lib/i18n.test.ts` fails when a key is missing in Arabic or
  left in English. Every plan that adds keys adds both languages.
- Unit tests are `vitest`, live in `lib/**/*.test.ts`, and need no database. Pure logic
  goes in its own module so it can be tested; database access is thin and untested.
- Route Handlers check the session with `rejectUnauthenticated(request, d)` from
  `lib/api.ts`, and answer errors through `errorResponse(err, d)` / `badRequest(...)`.
  Pages check with `requireAuth()` from `lib/auth/server.ts` (the `(app)` layout already
  does this for every page under it).
- Schema changes go into `schema.sql` in the "migrations" section as idempotent
  statements (`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`, the `DO $$`
  block for CHECK constraints). The file must still run clean on an empty database and
  on the current production one.
- Settings live in the single `settings` row. Adding a setting means: column in
  `schema.sql`, `SettingsRow` + `PublicSettings` + `SettingsPatch` + `WRITABLE` +
  `loadSettings` SELECT + `toPublicSettings` in `lib/settings.ts`, the zod schema in
  `app/api/settings/route.ts`, the form in `components/SettingsForm.tsx`, and the
  `settings.fields` labels in both dictionaries.
- The proxy (`proxy.ts`) sends every page without a session to `/login` and every API
  route without one to 401, except the `PUBLIC_API` set and `PUBLIC_PAGES` set. A plan
  that adds a public route adds it there.
- The user commits manually. No plan step commits. A task ends when `pnpm test`,
  `pnpm lint` and `pnpm exec tsc --noEmit` pass.

## Shared contract 1: the `alerts` table and `lib/alerts/log.ts` (owned by plan 01)

```sql
CREATE TABLE IF NOT EXISTS alerts (
  id          SERIAL PRIMARY KEY,
  kind        TEXT NOT NULL,          -- see AlertKind below
  level       INTEGER,                -- threshold percent for threshold kinds, else NULL
  scope_key   TEXT NOT NULL,          -- what the alert is about: 'YYYY-MM-DD' for a day,
                                      -- the cycle start 'YYYY-MM-DD' for a cycle, 'link' for
                                      -- the stale-router alert, 'digest:YYYY-MM-DD' for a digest
  channel     TEXT NOT NULL DEFAULT 'email',
  recipient   TEXT,
  subject     TEXT NOT NULL,
  status      TEXT NOT NULL CHECK (status IN ('sent', 'failed', 'skipped')),
  error       TEXT,
  payload     JSONB,                  -- the figures the message carried, for the history page
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS alerts_created_at_idx ON alerts (created_at DESC);
CREATE INDEX IF NOT EXISTS alerts_kind_scope_idx ON alerts (kind, scope_key);
```

```ts
// lib/alerts/log.ts
export type AlertKind =
  | "daily_threshold"   // 50 %, 80 %, ... of the daily window quota
  | "daily_exceeded"    // 100 % of the daily window quota (the alert that exists today)
  | "cycle_threshold"   // percent of the monthly cap
  | "cycle_pace"        // projected to exhaust the cap before the cycle ends
  | "link_stale"        // no push from the router for longer than settings allow
  | "link_recovered"    // pushes resumed after a link_stale alert
  | "digest";           // the scheduled summary

export type AlertStatus = "sent" | "failed" | "skipped";

export interface AlertEntry {
  kind: AlertKind;
  level: number | null;
  scopeKey: string;
  channel?: "email";          // the only channel for now
  recipient: string | null;
  subject: string;
  status: AlertStatus;
  error?: string | null;
  payload?: Record<string, unknown> | null;
}

export interface AlertLogRow {
  id: number;
  kind: AlertKind;
  level: number | null;
  scope_key: string;
  channel: string;
  recipient: string | null;
  subject: string;
  status: AlertStatus;
  error: string | null;
  payload: Record<string, unknown> | null;
  created_at: Date;
}

export function recordAlert(entry: AlertEntry): Promise<AlertLogRow>;
export function listAlerts(limit: number, beforeId?: number | null): Promise<AlertLogRow[]>;
/** The most recent row of a kind, optionally narrowed to a scope key. */
export function latestAlert(kind: AlertKind, scopeKey?: string): Promise<AlertLogRow | null>;
```

## Shared contract 2: `lib/alerts/dispatch.ts` (owned by plan 01, used by 02)

One function sends an email and records the outcome, so the log is never out of step
with what was actually sent.

```ts
// lib/alerts/dispatch.ts
import type { RenderedEmail } from "@/lib/email-template";

export interface DispatchInput {
  kind: AlertKind;
  level: number | null;
  scopeKey: string;
  to: string | null;             // null = no recipient configured; recorded as 'skipped'
  email: RenderedEmail;          // already rendered: subject, text, html
  payload?: Record<string, unknown> | null;
}

export interface DispatchResult {
  status: AlertStatus;
  row: AlertLogRow;
}

/** Sends through lib/email.ts `sendRendered` and records the row. Never throws on a
 *  send failure: the failure is the row's status and error. Throws only if the log
 *  insert itself fails. */
export function dispatchAlert(input: DispatchInput): Promise<DispatchResult>;
```

`lib/email.ts` gains one export used by the dispatcher:

```ts
export function sendRendered(to: string, email: RenderedEmail): Promise<string>; // returns the provider id
```

## Shared contract 3: settings columns added across plans

| Column | Type and default | Added by | Meaning |
| --- | --- | --- | --- |
| `alert_thresholds` | `INTEGER[] NOT NULL DEFAULT '{50,80,100}'` | 01 | Percent marks of the daily quota that trigger a mail. 100 is the existing "exceeded" alert. Sorted ascending, each 1..100, unique. |
| `cycle_alert_thresholds` | `INTEGER[] NOT NULL DEFAULT '{80,100}'` | 01 | Percent marks of the monthly cap that trigger a mail. |
| `cycle_pace_alert` | `BOOLEAN NOT NULL DEFAULT true` | 01 | Mail once per cycle when the projection first crosses the cap. |
| `stale_after_minutes` | `INTEGER NOT NULL DEFAULT 10 CHECK (stale_after_minutes BETWEEN 0 AND 1440)` | 02 | Minutes without a push before the link_stale alert. 0 disables. |
| `digest` | `TEXT NOT NULL DEFAULT 'weekly' CHECK (digest IN ('off','weekly','cycle'))` | 02 | Scheduled summary: never, every Monday, or the day after the cycle rolls over. |
| `throttle_on_breach` | `BOOLEAN NOT NULL DEFAULT false` | 03 | Tell the router to throttle when the daily quota is exceeded inside the window. |
| `throttle_on_cap` | `BOOLEAN NOT NULL DEFAULT false` | 03 | Tell the router to throttle when the monthly cap is exceeded. |
| `retention_days` | `INTEGER NOT NULL DEFAULT 90 CHECK (retention_days BETWEEN 7 AND 3650)` | 06 | Readings older than this are thinned to one per hour. |
| `share_token` | `TEXT` | 07 | Random token for the read-only page and JSON feed; NULL = sharing off. |
| `devices_enabled` | `BOOLEAN NOT NULL DEFAULT false` | 05 | Whether the Devices page is shown and device pushes are stored. |

Each plan adds only its own rows to `SettingsRow`, `PublicSettings`, `SettingsPatch`,
`WRITABLE`, the SELECT in `loadSettings`, `toPublicSettings`, the zod schema and the form.

## Shared contract 4: per-day and per-cycle alert state (owned by plan 01)

```sql
ALTER TABLE daily_windows ADD COLUMN IF NOT EXISTS notified_level INTEGER NOT NULL DEFAULT 0;
-- notified stays: it is true exactly when notified_level >= 100, and older queries read it.

CREATE TABLE IF NOT EXISTS cycle_alerts (
  cycle_start     DATE PRIMARY KEY,   -- local date the cycle began
  notified_level  INTEGER NOT NULL DEFAULT 0,
  pace_notified   BOOLEAN NOT NULL DEFAULT false,
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Pure helper both threshold features share:

```ts
// lib/alerts/thresholds.ts
/** The highest configured threshold that `percent` has reached and that is above
 *  `notifiedLevel`, or null when there is nothing new to say. Skipped marks are
 *  folded into the highest one, so a jump from 40 % to 95 % sends one 80 % mail,
 *  not a 50 % and an 80 %. */
export function nextThreshold(percent: number, notifiedLevel: number, thresholds: number[]): number | null;
/** Validation used by the settings route: integers, 1..100, ascending, unique, at most 8. */
export function isThresholdList(value: unknown): value is number[];
```

## Shared contract 5: the scheduler tick (owned by plan 02, used by 06)

```
POST /api/cron/tick        Authorization: Bearer $CRON_SECRET
GET  /api/cron/tick        same header (Vercel Cron and GitHub Actions send GET)
```

Response: `{ "ran_at": ISO, "jobs": [{ "name": string, "status": "ok" | "failed" | "skipped", "detail": string | null, "ms": number }] }`.

```ts
// lib/cron/jobs.ts
export interface JobContext { now: Date; settings: SettingsRow; }
export interface JobResult { status: "ok" | "failed" | "skipped"; detail?: string | null; }
export interface Job { name: string; run(ctx: JobContext): Promise<JobResult>; }
export const JOBS: Job[];   // filled by JOBS.push: plan 02's "stale" and "digest", then plan 06's "thinReadings"
```

```sql
CREATE TABLE IF NOT EXISTS job_runs (
  job          TEXT PRIMARY KEY,
  last_run_at  TIMESTAMPTZ NOT NULL,
  last_status  TEXT NOT NULL,
  last_detail  TEXT
);
```

The tick runs every job in sequence, records each non-skipped result in `job_runs`
(so `last_run_at` is the last time the job did work or failed), and never lets one
job's failure stop the next. Jobs register themselves with `JOBS.push(job)` at module
load, and `lib/cron/tick.ts` imports each job module for that side effect; the import
order is the run order. It is safe to call every minute or once a day; each job
decides from `job_runs` and its own state whether there is anything to do.

Triggers, all optional and all calling the same endpoint:
- `vercel.ts` cron entry `{ path: "/api/cron/tick", schedule: "*/5 * * * *" }` (needs a
  Vercel plan with sub-daily crons; on Hobby it runs once a day, which is enough for the
  digest and the thinning but not for the stale alert).
- `.github/workflows/tick.yml` on `schedule: "*/5 * * * *"` doing `curl -fsS -H
  "Authorization: Bearer $CRON_SECRET" https://netmonitor.bilalnasr.com/api/cron/tick`.
  Free and plan-independent; GitHub delays it by a few minutes under load.
- `docker-compose.yml` service `tick` for self-hosting: `curlimages/curl` in a
  `while true; do curl ...; sleep 60; done` loop.

## Shared contract 6: the ingest response policy (owned by plan 03)

`/api/ingest` keeps every field it returns today and adds:

```json
"policy": { "throttle": false, "reason": null }
```

`reason` is `"daily_quota"`, `"monthly_cap"` or `null`. The router script reads the
body with `as-value` and looks for the literal `"throttle":true`.

## Shared contract 7: per-device tables (owned by plan 05)

```sql
CREATE TABLE IF NOT EXISTS devices (
  mac         TEXT PRIMARY KEY,           -- upper-case, colon-separated
  name        TEXT,                       -- user-given label; NULL = use last hostname
  hostname    TEXT,                       -- last DHCP host-name seen
  ip          TEXT,
  first_seen  TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_seen   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS device_readings (
  id           SERIAL PRIMARY KEY,
  recorded_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  mac          TEXT NOT NULL REFERENCES devices (mac) ON DELETE CASCADE,
  tx_bytes     BIGINT NOT NULL,           -- counters as the router reports them (cumulative)
  rx_bytes     BIGINT NOT NULL
);
CREATE INDEX IF NOT EXISTS device_readings_mac_recorded_idx ON device_readings (mac, recorded_at, id);
```

Push endpoint: `POST /api/ingest/devices` with the same bearer token, body
`{ "router_time": "...", "devices": [{ "mac": "AA:BB:...", "ip": "192.168.88.10", "name": "phone", "tx_bytes": 123, "rx_bytes": 456 }] }`.
Usage per device uses the same delta rule as `interface_readings` (growth of the counter,
or the whole value when it went backwards), partitioned by `mac`.

## Shared contract 8: the share token (owned by plan 07)

- `GET /[lang]/share/[token]` renders the dashboard read-only (no nav, no settings).
- `GET /api/share/[token]/usage` returns `TodayUsage` plus `CycleUsage` as JSON with
  `Cache-Control: no-store`, for Home Assistant's REST sensor and similar.
- Both are public in the proxy; the token is compared in constant time.
